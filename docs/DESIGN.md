# 架构决策记录（ADR）

## ADR-001：SQL 生成与执行分离

**决策**：LLM 只输出 SQL 文本 + 解释 + 假设，不直接连库执行。执行走独立通道：只读账号 → 语法校验 → `EXPLAIN` 预检 → 加 `LIMIT` → 超时 5s → 行数上限 500。

**理由**：提示注入可以让模型生成 `DROP TABLE`。把"生成"和"执行"拆开，模型被攻破时损失可控。这也是企业客户第一个会问的问题。

**代价**：多一层代码，多一次往返。值得。

## ADR-002：先只支持 MySQL

**决策**：v0.1 只做 MySQL 8，schema 读取用 `information_schema`。

**理由**：多数据库支持会让 prompt 和类型映射复杂度翻倍，而验收标准只看 MySQL 就够。PostgreSQL 放 W5 之后。

## ADR-003：评测集先行

**决策**：W3 先写 30 条"中文问题 → 期望 SQL 语义"，再写生成逻辑。

**理由**：没有评测集，改 prompt 全靠感觉。评测集是判断"变好还是变坏"的唯一依据，也是面试时最硬的证据。

**怎么做**：每条记 `{问题, 期望涉及的表, 期望过滤条件, 是否可执行}`，用 LLM 辅助判分 + 人工抽检 10 条。

## ADR-004：不用 LangChain4j / Spring AI 的 Agent 抽象

**决策**：W2 用 Spring AI 的 `ChatClient`，但不使用其 Agent / 工具编排抽象，工具调用自己写。

**理由**：学习阶段抽象层越薄越好，出问题能定位。等 P2 再评估框架。
